# 1.0.0 — gates and decision record

1.0.0 is a promise about the public API and about behavior against a spec that the maintainer describes as still in beta upstream. The gates below are necessary; the decision record says whether 1.0.0 should be tied to the upstream spec status at all.

*Sizes:* S ≤ 2 days, M ≈ 1–2 weeks, L > 2 weeks. *Gates:* spec, API, interop, security, DevSecOps usability, maintenance (see `docs/roadmap-gap-analysis.md`). Milestones are planning targets, not commitments.

## Decision record: 1.0.0 versus upstream TEA beta

**Context.** The pinned OpenAPI file says `info.version: 1.0.0` (`spec/PINNED.md`, commit date 2026-10-08), but the maintainer describes upstream TEA as still in beta. This repository cannot confirm the upstream status (no network use here), so the premise is recorded as maintainer-stated. A crate that calls itself 1.0.0 promises its own API stays compatible; if the upstream wire format can still change, that promise either forces frequent major releases or hides breakage behind lenient parsing.

**Options.**

| Option | What it means | For | Against |
| --- | --- | --- | --- |
| A. Stay 0.x until upstream is stable | Publish 0.1.0 now; keep minor releases (0.2 …) for breaking changes; cut 1.0.0 only after upstream declares stability | Honest about the risk; 0.x minor bumps are the normal channel for breaking changes; no pressure to freeze models | Some adopters avoid 0.x; DevSecOps teams may pin forever |
| B. Cut 1.0.0 on our gates, with a written re-pin policy | 1.0.0 when the gates above are met; a re-pin that breaks models ships as 2.0.0 (or as a new `libtea-core` major); `lenient_versions` and tolerant parsing absorb additive changes | Signals maturity; policy makes expectations explicit | Risks a 2.0.0 soon after 1.0.0; `non_exhaustive` models only reduce, not remove, that risk |
| C. Split | `libtea-core` models stay 0.x (they track the spec); `libtea-client` and the CLI go 1.0.0 on a thin, stable surface | Matches where change actually happens | Two version lines; client re-exports core types, so a core 0.x bump is still a client breaking change |

**Recommendation.** Option A. Publish 0.1.0 now with the re-pin policy written down (0.2-1, `docs/re-pinning.md`), keep every spec-driven break in a 0.x minor, and decide 1.0.0 when (1) the gates in `docs/milestones/1.0.md` are met and (2) upstream has declared the spec stable or has gone a full release cycle without wire changes. If upstream stays in beta for a long time, fall back to option B with the written re-pin policy rather than waiting indefinitely. Do not choose C: the client re-exports core types, so the split does not isolate the risk.

**Revisit when:** the upstream repository tags a stable release, the pinned commit changes, or an interop partner asks for a stability guarantee.
