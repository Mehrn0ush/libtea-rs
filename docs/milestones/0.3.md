# 0.3 — CLI for CI

Make the CLI something a pipeline can depend on: documented, tested output and exit codes; selection, streaming download, a lock file, sync/diff; then ship it (Action, binaries, image). Order inside the milestone follows the dependencies: the lock file needs streaming hashes and artifact selection.

*Sizes:* S ≤ 2 days, M ≈ 1–2 weeks, L > 2 weeks. *Gates:* spec, API, interop, security, DevSecOps usability, maintenance (see `docs/roadmap-gap-analysis.md`). Milestones are planning targets, not commitments.

## 0.3-1 Documented, tested JSON schemas

- **Why:** Output shapes are ad hoc `serde_json::json!` values with no schema or test.
- **Size:** M (about 1–2 weeks)
- **Gate:** DevSecOps usability
- **Depends on:** none
- **Acceptance criteria:**
  - [ ] `docs/cli-json.md` (done in F1) and `docs/schemas/*.json` (not yet) describe every `--json` output and the `conformance` report
  - [ ] a test per command validates real output against its schema
  - [ ] a change to a field name fails a test

## 0.3-2 Documented exit codes

- **Why:** Codes today: 0, 1, 4; not in `--help` or the README; no code separates auth, not-found, integrity, or policy failures.
- **Size:** S (≤ 2 days)
- **Gate:** DevSecOps usability
- **Depends on:** 0.3-1
- **Acceptance criteria:**
  - [x] table in `docs/cli-exit-codes.md` and in `libtea --help` (done in F1)
  - [ ] distinct codes for usage, auth, not found, integrity failure, weak-only checksums are done (2, 3, 5, 6, 4); network and policy refusal are still 1 (open question 18); 7 is reserved for changes detected and not yet emitted
  - [x] a test asserts each emitted code (`crates/tea-cli/tests/json_and_exit_codes.rs`); 7 is checked only in `--help`

## 0.3-5 Streaming download with incremental hashing

- **Why:** The artifact is buffered in a `Vec` (up to 256 MiB × `max_in_flight`) and hashed afterwards.
- **Size:** L (more than 2 weeks)
- **Gate:** DevSecOps usability
- **Depends on:** none
- **Acceptance criteria:**
  - [x] new API writes to a caller-supplied sink (file) while feeding `ChecksumVerifier` (`Service::download_*_to_file`, `download_format_to_writer`; experimental)
  - [ ] peak memory stays below a stated bound in a test with a body larger than the bound (not measured; no bound is claimed)
  - [x] a checksum mismatch removes the partial file; size limits apply to encoded and decoded bytes while streaming (`crates/tea-client/tests/streaming_download.rs`)

## 0.3-7 Lock file

- **Why:** No record of what was fetched.
- **Size:** M (about 1–2 weeks)
- **Gate:** DevSecOps usability
- **Depends on:** 0.3-4, 0.3-5
- **Acceptance criteria:**
  - [x] lock (`docs/lock-file.md`, `docs/schemas/lock-v1.schema.json`, key names checked by `crates/tea-cli/tests/lock_schema.rs`) records TEI, redacted server base URL, API version, spec commit, product release, collection version, and per artifact format: uuid, revision, type, media type, size, declared checksums, integrity outcome, fetchedAt. **Deliberately not recorded** (F2 decision): the content URL (may carry a signed query), the client version and the ETag; add them in a later `schemaVersion` if a user needs them. The file is `schemaVersion` 1, not named `tea.lock` by the tool: the path is `--lock`
  - [x] written atomically; deterministic ordering; no secrets (`crates/tea-core/src/lock.rs` unit tests and proptest, `crates/tea-cli/tests/sync.rs`)
  - [x] round-trip test (unit test, proptest, and the `lock_parse` fuzz target)

## 0.3-8 `sync` and `diff`

- **Why:** No way to refresh a lock or see what changed.
- **Size:** L (more than 2 weeks)
- **Gate:** DevSecOps usability
- **Depends on:** 0.3-7, 0.3-2
- **Acceptance criteria:**
  - [x] `libtea diff old.lock new.lock` compares two locks offline and prints added/changed/removed entries (JSON and text); exit 7 when they differ. **Changed from the plan:** it compares two lock files, not a lock and the server; the server comparison is `sync --check`
  - [x] `libtea sync` resolves, downloads every format, verifies, and writes the lock; `sync --check` (this item's `--frozen`) fails with exit 7 if the lock would change. **Changed from the plan:** `sync` re-downloads everything; it does not fetch only what changed
  - [ ] conditional requests are used where ETags are present (not done: the lock keeps no ETag, open question 21)
